# Card dependencies and blocking rules

Add directed dependencies between published cards within the same board so work cannot be closed before its prerequisites are complete.

An authorized editor can add and remove prerequisites from a card detail page. The page lists both "Blocked by" prerequisites and "Blocking" dependents, with links and current open/closed state. Offer only accessible published cards in the same board. Reject self-links, duplicate links, links to another board/account, unpublished targets, and any link that would create a cycle, including cycles of three or more cards. Rejection must leave existing links intact and explain the problem without disclosing inaccessible cards.

A card is blocked if at least one prerequisite is open. Show a blocked badge and open-prerequisite count on its board preview. Add a "Blocked" filter to the existing card filtering experience, composable with board, assignee and tag filters and pagination. A blocked card cannot be closed through any existing web or JSON closure path, including column/drop interactions. This rule applies to direct crafted requests too. Once every prerequisite is closed, the dependent can be closed normally.

Reopening a prerequisite must not automatically reopen its already-closed dependents; they remain closed, but their detail page shows their currently open prerequisites. Open dependents immediately become blocked again. Removing a dependency immediately updates blocking. Deleting a prerequisite removes its links and leaves remaining prerequisites effective. Moving a card that has any incoming or outgoing dependency to another board is refused until those links are removed; moving an unlinked card still works.

Persist relationships across restarts and keep all reads/writes account- and board-scoped. Concurrent opposite-edge additions must not create a cycle; concurrent closure and prerequisite reopening must leave a result consistent with some serial ordering of those operations. Demonstrate these invariants in deterministic tests. Existing cards without dependencies retain existing behavior. Cover relevant model, request and browser behavior with tests; no external service, notification system, cross-board dependencies, or dependency visualization is required.

Execution contract: Work in the existing Fizzy application and follow its ordinary project style. Implement this feature, add scoped regression tests, and run the checks appropriate to your changes. Preserve existing behavior and account/board authorization. Use locally controlled infrastructure; do not add hosted services. Do not publish, deploy, or push unless the operator separately authorizes it. Ask the operator when blocked; do not silently reduce scope. Report the behavior delivered, tests run, and remaining limitations when ready for review.
